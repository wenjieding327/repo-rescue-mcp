# RepoRescue 复赛商业验证计划（14 天）

## 1. 决策

复赛前应做的是**商业化验证**，不是上线支付、扩大投放或包装成成熟 SaaS。

当前优先顺序：

1. 证明目标用户确实频繁遇到“代码/仓库跑不通”的问题。
2. 证明 RepoRescue 能稳定交付可理解、可核验的结果。
3. 测出一次服务的真实成本和用户愿意接受的价格区间。
4. 再决定学生订阅、机构采购或实验室服务哪条路径值得继续。

核心定位与现有文档一致：普通代码急救负责低门槛体验，公开仓库复现与验证负责技术护城河；产品卖点不是“比通用 AI 更会写代码”，而是固定的失败复现、最小修复、同用例重测和分级证据。

## 2. 当前真实能力基线

### 已有源码与历史证据

- 历史 Node 部署曾取得安全 Python 片段前后验证和 Click 指定测试证据；最新公开页面回归出现工具缺失，因此必须先完成 v4 重部署验收，不能把历史证据当成当前在线能力。
- 本地 v0.3.0 候选：已实现仓库分析、Docker verifier、服务端/宿主 Repair Agent、有界补丁、同命令重测和 artifact 输出的代码路径。
- 内置可信 Demo：可稳定生成 `repair.patch`、`evidence.json` 和 `report.md`，证明编排和证据协议可运行。
- 已有自动化测试覆盖不安全导入、无限循环预算、路径穿越、测试文件修改、远程依赖和不规范 GitHub URL 等边界。

### 尚不能默认宣称

- 线上星辰 Agent 已经调用 v0.3.0 完整仓库闭环。
- Docker + 真实 Repair LLM 已对任意外部故障仓库稳定成功。
- 支持任意语言、私有仓库、GPU、数据库或所有依赖类型。
- 已有真实活跃用户、付费客户、收入或经测量的节省时间。

商业验证的所有对外材料都必须以这一基线为起点。

## 3. 要验证的三个核心假设

### H1：问题真实且高频

学生、助教和实验室成员会花费显著时间处理环境、依赖、入口、路径和测试失败，而通用聊天模型不能稳定提供可执行证据。

### H2：用户重视“验证”而不只是“答案”

用户愿意为了修改前失败、修改后同用例通过、完整 Diff 和可复现报告，选择 RepoRescue 而非仅复制聊天建议。

### H3：至少一个付费主体成立

- 学生愿意为有限的仓库级救援付小额订阅或按次费用；或
- 助教/课程负责人愿意为批量诊断、统一证据和减少排障时间购买课程方案；或
- 实验室愿意为公开科研仓库的受控复现与报告付费。

三条中只需一条得到初步支持，不要求复赛前证明完整商业规模。

## 4. 目标用户和首要场景

| 用户 | 高频任务 | 当前价值主张 | 可能付费者 |
|---|---|---|---|
| 编程初学者/课程学生 | 片段报错、作业测试失败、陌生项目跑不通 | 不要求懂命令或提示词，直接得到原因、最小修改和实际重测 | 学生本人、课程 |
| 助教/教师 | 重复处理环境问题、定位是否为代码错误、核对学生修复 | 标准化复现命令、证据等级和报告，减少重复排障 | 院系、课程、实训平台 |
| 实验室/研究生 | 接手公开科研仓库、README 不完整、依赖或路径不匹配 | 固定 commit、区分可修与需授权部分、输出可复现边界 | 实验室、科研项目 |

复赛前以学生和助教为主，实验室场景只验证需求与 P1—P3 复现价值，不承诺论文指标 P5。

## 5. 访谈计划

### 样本

- 学生：5—10 名，至少包含 2 名初学者、2 名做过课程/竞赛项目的学生、1 名研究生或科研助理。
- 助教/教师：2 名，优先选择近期需要指导编程作业、课程项目或实验室新人的人员。
- 每次 20—30 分钟；访谈后再让其中部分用户完成试用任务。
- 使用参与者编号记录，不在公开材料中保存姓名、学号、邮箱、仓库凭据或未脱敏代码。

### 学生访谈问题

1. 最近一次代码或 GitHub 项目跑不通是什么时候？当时要完成什么任务？
2. 故障属于代码、依赖、环境、路径、数据、文档还是不确定？
3. 从遇到问题到解决或放弃一共用了多久？请给实际时间区间。
4. 你依次用了哪些办法：搜索、问同学、问助教、聊天模型、重新安装环境等？
5. 现有 AI 给出的建议最常见的问题是什么：不能运行、改坏接口、解释太难、没有证据，还是其他？
6. 看到“修改前失败、修改后同一测试通过”是否会提高信任？还需要看到哪些信息？
7. 你是否愿意提交公开仓库 URL？哪些隐私或安全问题会阻止你使用？
8. 片段急救和完整仓库救援中，哪一个对你更有价值？为什么？
9. 如果每月有免费额度，你预计会用几次？超过额度后更接受按次还是订阅？
10. 在实际体验后，从 `免费 / 9元 / 19元 / 39元每月 / 不会付费` 中选择最接近的区间，并说明原因。

价格问题必须放在体验之后，避免仅凭想象回答。

### 助教/教师访谈问题

1. 一门课或一个项目周期内，大约有多少学生因环境或运行问题求助？
2. 你每周花多少时间复现学生问题？请按最近一次课程实际情况估算。
3. 哪些问题最重复，哪些问题必须人工判断？
4. 你判断“真的修好”最低需要哪些证据：命令、退出码、测试数、Diff、环境版本还是完整日志？
5. 是否允许学生提交公开仓库？课程代码、作业答案和个人数据有哪些合规限制？
6. 如果系统只给 patch、不自动推送仓库，是否更容易纳入课程流程？
7. 你更需要学生自助入口，还是助教批量任务和统一报告？
8. 哪些错误成功或安全事故会让你立即停止使用？
9. 是否愿意在一个小作业中做 2—4 周、人数和次数受限的试用？需要什么审批？
10. 如果试用确实减少排障时间，更适合按学生、按课程、按运行次数还是学校年度授权采购？可接受的预算由谁决定？

不得把“愿意试用”写成付费意向，更不能写成客户或订单。

## 6. 三个试用任务

### 任务 A：学生片段急救

**入口**：完成 v4 重部署并通过公开回归后的 Node MCP；验收前只用本地候选版，不把旧公开页面当作可用入口。

**输入**：一个存在索引、类型或循环问题的安全 Python 片段，并提供明确预期输出。

**成功证据**：

- 原片段在同一用例真实失败。
- 候选代码通过该用例。
- 页面给出小白能懂的原因和完整可复制代码。
- 证据等级只写 S2/片段级验证，不扩展到项目。

**参与者**：至少 5 名学生各完成 1 次。

### 任务 B：课程仓库救援

**入口**：本地或受控托管的 v0.3.0 Docker + Repair Agent。

**输入**：团队自己控制的公开 Python 故障仓库，固定 commit，包含一个真实失败测试；缺陷不得靠删除测试或硬编码答案修复。

**成功证据**：

- 记录仓库 URL、commit、环境、完整验证命令和修改前退出码。
- Repair Agent 只修改允许的现有非测试文件。
- Verifier 使用完全相同的命令重测。
- 输出 patch、机器证据和人工报告。
- 从干净环境至少独立重复 2 次。

**参与者**：2—3 名学生和至少 1 名助教查看结果并评价可信度。

这是商业验证任务，不得在完成前写成现有成功案例。

### 任务 C：实验室公开仓库复现评估

**入口**：公开仓库检查和受控复现。

**输入**：由研究生或助教提供一个公开、无敏感数据的 Python 科研/课程仓库。

**目标**：固定 commit，识别入口、版本、依赖、数据和外部服务边界，并尝试达到 P1—P3；只有实际跑通官方 Demo 才能写 P4。

**成功也可以是有证据的阻塞**：如果缺数据、权重、GPU 或授权，报告必须明确停止位置、已验证事实和下一步所需条件，不能生成虚假成功。

**参与者**：1 名研究生/科研助理和 1 名助教共同核对报告是否有用。

## 7. 指标记录表

每一次访谈和任务都用参与者编号，保留分子/分母，避免小样本只报百分比。

| 字段 | 记录方式 |
|---|---|
| 参与者 | `S01`—`S10`、`TA01`—`TA02`，不记录公开身份信息 |
| 用户类型 | 初学者、项目学生、研究生、助教 |
| 任务 | A、B 或 C |
| 输入范围 | 片段或已脱敏的公开仓库 URL + commit |
| 开始/结束时间 | ISO 时间；计算总耗时 |
| 首次有效结果时间 | 首次出现可执行诊断或真实失败证据的时间 |
| 原始状态 | 错误类型、命令、退出码、超时、缺失条件 |
| 最终状态 | 已验证修复、仅运行、阻塞、失败或未执行 |
| 证据等级 | S1/S2 或 P1—P5，按实际范围填写 |
| 修改范围 | 文件数、行数、是否触及测试（应为否） |
| 人工介入 | 次数、原因、耗时 |
| 错误成功 | 是否在证据不足时声称成功；目标必须为 0 |
| 可信度评分 | 体验后 1—5 分，并记录原因 |
| 易用性评分 | 体验后 1—5 分，并记录卡点 |
| 是否愿意再次使用 | 是/否/不确定 + 原因 |
| 价格反馈 | 免费、按次、月订阅、机构付费及可接受区间 |
| 模型用量 | 模型、输入/输出 token、重试次数 |
| 计算用量 | 容器分钟、CPU/内存上限、安装与执行时间 |
| artifact | patch/report/evidence 路径和 SHA-256 |

必须同时保存失败任务；不得只挑成功案例进入汇总。

## 8. 成本核算

复赛前不预填单位成本，按每次真实任务记录：

```text
单次变动成本
= 模型输入 token × 单价
+ 模型输出 token × 单价
+ 容器运行分钟 × 内部计算单价
+ artifact 存储与出网成本
+ 需要人工介入的分钟 × 试算人工成本
```

至少分别计算：

- 片段急救成本。
- 成功的仓库救援成本。
- 失败/超时仓库任务成本。
- P1—P3 仓库复现评估成本。

商业可行性不能只看成功任务；失败任务同样消耗模型和容器资源。

## 9. 免费额度与定价假设

以下只是待访谈和成本验证的价格卡，不是已上线价格或收入预测。

### 免费体验

- 无需注册：每天 1 次短 Python 片段急救。
- 注册学生：每月 10 次片段急救。
- 内置项目 Demo 不限查看，但明确标记为确定性样例。
- 在滥用控制、成本和隔离验收前，不向匿名用户开放任意仓库执行。

### 学生方案假设

- `19—39 元/月`，包含有限的公开仓库救援额度。
- 或 `9—29 元/次` 的仓库级 verified rescue。
- 具体次数必须在测得失败任务成本后确定，不能先承诺“无限次”。

### 课程/机构方案假设

- 先做 2—4 周、人数和运行次数封顶的免费或成本价试点。
- 验证后测试两种报价：
  - `30—80 元/活跃学生/学期`；或
  - `3000—10000 元/课程/学期`，包含明确任务上限。
- 机构价值以实际减少的重复排障时间、统一报告和安全边界衡量，不以模型 token 数宣传。

### 实验室方案假设

- 按公开仓库复现评估或 verified rescue 单次计费。
- 只有能稳定交付 P3/P4 报告并测出人工成本后再报价。
- P5 论文指标复现不进入首版承诺。

## 11. 成功门槛

小样本结论必须同时报告人数，例如 `4/6`，不能只写 `67%`。

### 问题与需求门槛

- 至少 `60%` 的受访学生在最近一个月遇到过超过 30 分钟的代码/环境排障。
- 至少 `3/5`（若访谈 10 人则至少 `6/10`）在体验后愿意再次使用。
- 至少 `1/2` 助教愿意讨论一个人数和次数受限的课程试点。

### 产品门槛

- 任务 A 的 S2 完成率至少 `80%`，并且错误成功为 `0`。
- 任务 B 从干净环境独立完成至少 2 次，前后命令一致、测试未修改、artifacts 完整。
- 任务 C 能输出边界清楚的 P1—P3 结果；缺条件时必须准确停止。
- 所有任务的错误成功数必须为 `0`。任何一次错误标记 verified 都先阻断公开仓库自动修复。

### 成本门槛

- 每类任务均能在 `±20%` 范围复算模型、容器和人工变动成本。
- 预计变动成本不高于所测试最低可接受价格的 `30%`；否则减少免费额度、限制任务或调整模型/执行策略。

## 12. 停止或转向门槛

- 出现任意一次“未通过却标记 verified”：立即暂停公开自动修复，优先修证据协议。
- 任务 B 无法在干净环境重复成功：复赛只展示片段和内置 Demo，不宣称真实仓库闭环已上线。
- 少于 `40%` 学生愿意再次使用：暂停学生订阅假设，重新检查入口、语言和痛点。
- `0/2` 助教愿意继续试点：后置机构采购，先验证学生自助或实验室服务。
- 用户普遍不愿提供公开仓库：转向本地执行、文件上传或学校私有部署研究，不强推云端仓库模式。
- 失败任务成本接近或超过可接受价格：关闭免费仓库执行，改成付费前预检查或只读诊断。
- 为了达到成功率需要修改测试、硬编码答案或隐瞒失败：停止该任务，不调整证据口径。

## 13. 数据与宣传边界

### 可以记录

- 脱敏后的错误类型、公开仓库 URL、commit、命令、退出码和时间。
- 参与者编号、用户类型、评分和经同意的匿名反馈。
- 真实 token、容器分钟、重试、人工介入和 artifact 哈希。

### 不得记录或公开

- 姓名、学号、私人邮箱、私有仓库地址、API key、token 和未授权课程答案。
- 未经同意的录音、截图、仓库内容或可识别引用。

### 不得虚构

- 用户数、活跃度、留存率、付费率、收入、客户和合作关系。
- 自动修复成功率、节省时间、单位成本和市场规模。
- Docker/线上星辰/真实模型成功状态。
- P4 官方 Demo 或 P5 论文指标。

访谈意向不等于购买，免费试用不等于客户，内置 Demo 不等于任意 GitHub 修复。

## 14. 复赛商业页最终只回答五件事

1. 谁遇到这个问题，以及真实频次和耗时是多少。
2. RepoRescue 相比聊天建议多交付了什么可核验证据。
3. 三个任务实际完成了多少，失败在哪里。
4. 一次服务的真实变动成本和用户反馈价格区间。
5. 接下来选择学生、课程还是实验室路径，以及为什么。

如果数据不足，直接写“验证中”和下一步，不用未经测量的市场数字填空。
